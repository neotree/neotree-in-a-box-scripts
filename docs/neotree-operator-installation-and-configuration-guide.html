Neotree In-A-Box Operator Installation and Configuration Guide

Audience: Ministry teams, facility implementation teams, programme managers, and approved system operators.

Purpose: To provide clear installation, configuration, support, and basic troubleshooting guidance without requiring Neotree engineers to be present.

1. Document Scope

This guide explains how an approved operator can install and configure the Neotree In-A-Box services on an Ubuntu 24 server. It is written for operational use and avoids engineering detail where possible. The guide assumes that the Ministry or implementing partner has already approved the server, the intended health facility, and the responsible staff members.

The installation includes the Neotree API, WebEditor, Data Pipeline, and Metabase reporting service. These services work together to support local deployment, form management, data processing, and reporting. The full installer sets them up in this order: Neotree API first, WebEditor second, Data Pipeline third, and Metabase last.

2. Roles and Responsibilities

Role Responsibility
Ministry or programme owner Approves the deployment, confirms the facility details, confirms reporting requirements, and approves access to sensitive information.
System operator Runs the installation, records configuration choices, checks that the services start, and reports issues using the troubleshooting section.
Facility representative Confirms facility name, facility code, country, and the agreed admission and discharge workflows.
Database or server administrator Provides approved server access, backups, network access, and secure handling of passwords and certificates.

3. Before Installation

Complete the following checks before starting. These checks reduce interruptions and make the installation easier to complete in one session.

  1. Confirm that the server is running Ubuntu 24 and that the operator has approved sudo access.
  2. Confirm that the server has a stable internet connection during installation.
  3. Confirm that the server has enough storage for the application, reporting files, and logs.
  4. Confirm the country for the deployment. The current default is Malawi.
  5. Confirm the health facility code and name. The default test facility is code TH and name Test Hospital.
  6. Confirm whether the services will use a domain name, a public IP address, or local-only access.
  7. Confirm whether HTTPS certificates are already available. If certificates are not available, the advanced web setup can be skipped and completed later.
  8. Confirm who will hold the WebEditor administrator account and password.

4. Important Safety Notes

  • Do not share passwords, API keys, certificate keys, or database credentials in email or public chat channels.
  • Do not store patient-identifying information in this installation guide.
  • Use only Ministry-approved servers and Ministry-approved staff accounts.
  • Keep a written record of the installation date, server name, responsible operator, and selected facility details.
  • Do not run the cleanup script unless there is written approval, because it removes installed services and application files.

5. Installation Guide

5.1 Log in to the Server

Log in to the approved Ubuntu 24 server using the account provided by the server administrator. The account must be allowed to run administrative commands using sudo.

5.2 Place the Deployment Scripts on the Server

Place the Neotree In-A-Box deployment folder on the server. If the folder has already been copied, move into that folder before continuing.

cd neotree-in-a-box-scripts

5.3 Allow the Deployment Scripts to Run

Run the following command once. It allows the deployment scripts to start the required installation steps.

chmod -R +x deploy

5.4 Start the Full Installation

Run the full installation command below. The installer follows the same order every time: Neotree API, WebEditor, Data Pipeline, and Metabase.

bash deploy/deploy.sh

When prompted, choose the recommended express installation unless the Ministry or programme team has requested a custom setup. Express installation uses the standard defaults and avoids unnecessary questions.

5.5 Installation Order

The installation order matters because later services use information created by earlier services. Operators should allow the installer to complete each stage in the order shown below.

Order Component Plain-language purpose
1 Neotree API Creates the core service and database foundation used by the rest of the system.
2 WebEditor Sets up the form management service and seeds the starting form data.
3 Data Pipeline Creates the pipeline configuration, facility configuration, and automatic schedule for processing data.
4 Metabase Sets up the reporting service used to view dashboards and reports.

5.6 Respond to Prompts

The installer may ask whether to install missing packages. Choose yes when the package is part of the installation requirement. The installer may also ask whether to continue with advanced setup for domain names, email, web server configuration, and certificates. If these details are not ready, it is acceptable to skip advanced setup and complete it later.

5.7 Confirm Installation Completion

At the end of a successful installation, the deployer records progress and prints a success message. Logs are saved inside the deployment folder under each service. These logs should be kept for support and audit purposes.

deploy/node-api/logs/ deploy/webeditor/logs/ deploy/datapipeline/logs/ deploy/metabase/logs/

6. Configuration Guide

6.1 Main Application Location

By default, the installed applications are placed under the operator home directory in a folder named neotree. The usual location is shown below.

/home/ubuntu/neotree

If a different location is required, the operator may set the APP_ROOT value before running the installer. This should only be done when the Ministry or server administrator has agreed the location.

6.2 Shared Database Credentials

The installer creates shared database credentials for the Neotree services. These credentials are stored in the local application environment file. This file must be protected and must not be shared publicly.

~/neotree/.env

6.3 Data Pipeline Database Configuration

The Data Pipeline creates a local database configuration file. The file uses the Node API database details and the shared password. It also records the country, pipeline working directory, WebEditor address, and WebEditor API key.

~/neotree/datapipeline/conf/local/database.ini

The expected structure is shown below. Values may differ depending on the approved deployment.

[postgresql_dev] host = localhost database= nodeapi_prod user= neotree_app password= nodeapi-database-password country = malawi cron_dir = /home/ubuntu/neotree/datapipeline/ data_fix = false webeditor = http://localhost:3001 webeditor_api_key = protected-key-value

6.4 Facility Configuration

The Data Pipeline also creates a facility configuration file. The default test facility is Test Hospital with code TH. The country is taken from the selected deployment country. Admission and discharge script IDs are taken from seeded WebEditor data when available.

~/neotree/datapipeline/conf/local/hospitals.ini

The expected structure is shown below.

[TH] name= Test Hospital country= malawi admissions = admission-script-id discharges = discharge-script-id

For a real facility, replace the test facility details only with approved values. For example, Kamuzu Central Hospital may use facility code KCH and name Kamuzu Central Hospital. Changes should be recorded in the deployment record.

6.5 Data Pipeline Schedule

After the Data Pipeline is installed successfully, the installer creates a scheduled task that runs the pipeline every 30 minutes. The task uses the local pipeline working directory and the pipeline virtual environment.

*/30 * * * * cd /home/ubuntu/neotree/datapipeline && env/bin/python -m kedro run --env=dev

The installer manages this scheduled task automatically. Operators should not add duplicate scheduled tasks for the same pipeline.

6.6 WebEditor Configuration

The WebEditor is used to manage forms and seeded data. During setup, an API key is generated and stored. The same key is made available to the Data Pipeline so it can request WebEditor data. Keep this key private.

6.7 Metabase Configuration

Metabase is the reporting service. It uses its own application database and runs as a system service. On Ubuntu 24, Metabase requires Java 21 or newer. The deployer downloads a valid Metabase application file and checks that the file is usable before starting the service.

6.8 Public Web Access Using nginx

nginx is the web server used to make approved services available through a public address. In this deployment, WebEditor and Metabase are the public-facing services. WebEditor is used by approved staff to manage forms. Metabase is used by approved staff to view reports and dashboards. The Neotree API supports the system behind the scenes and does not normally need to be presented as a public page for general users.

Advanced setup can configure public web access through nginx and optional HTTPS certificates. If a domain is not ready, the setup can use the server public IP address. If certificates are not ready, plain HTTP can be used temporarily where approved by the Ministry or programme owner.

6.9 WebEditor nginx Setup

WebEditor nginx setup should be completed when the WebEditor needs to be accessed by approved users outside the server. The operator may complete this during WebEditor advanced setup, or later by running only the WebEditor nginx phase.

bash deploy/webeditor/phases/08_nginx_setup.sh

Before running this step, confirm the approved public address for WebEditor. This may be a domain name or the server public IP address. If using HTTPS, confirm that the certificate fullchain file and private key file are already available on the server.

Item What the operator should provide
Public address The approved WebEditor domain name, or blank if the approved public IP address should be used.
HTTPS certificate The path to the fullchain certificate file, if HTTPS is being enabled.
HTTPS private key The path to the private key file, if HTTPS is being enabled. This file must be handled securely.

After setup, nginx is tested and reloaded by the script. If the public address does not open, check that the domain points to the server, the firewall allows web traffic, and the WebEditor service is running.

6.10 Metabase nginx Setup

Metabase nginx setup should be completed when dashboards and reports need to be accessed by approved users through a public address. The operator may complete this during Metabase advanced setup, or later by running only the Metabase nginx phase.

bash deploy/metabase/phases/04_nginx_setup.sh

Before running this step, confirm the approved public address for Metabase. This may be a domain name or the server public IP address. If using HTTPS, confirm that the certificate fullchain file and private key file are already available on the server.

Item What the operator should provide
Public address The approved Metabase domain name, or blank if the approved public IP address should be used.
HTTPS certificate The path to the fullchain certificate file, if HTTPS is being enabled.
HTTPS private key The path to the private key file, if HTTPS is being enabled. This file must be handled securely.

After setup, nginx is tested and reloaded by the script. If the public address does not open, check that Metabase is running, the domain points to the server, and the firewall allows web traffic.

6.11 Public Access Checklist

  1. Confirm that only approved services are made publicly accessible.
  2. Confirm that WebEditor and Metabase addresses are recorded in the installation record.
  3. Confirm that certificate files are stored securely and are not copied into public folders.
  4. Confirm that Ministry or programme owners have approved any temporary plain HTTP access.
  5. Confirm that public access has been tested from an approved network.

7. What We Support and Do Not Support

7.1 Supported

  • Installation on an approved Ubuntu 24 server.
  • Deployment of the Neotree API, WebEditor, Data Pipeline, and Metabase using the provided scripts.
  • Standard local PostgreSQL setup using the shared Neotree application user.
  • Default Malawi-oriented configuration, including default test facility values where no real facility values have been approved.
  • Automatic creation of Data Pipeline configuration files.
  • Automatic scheduling of the Data Pipeline every 30 minutes.
  • Optional nginx and TLS setup when domain and certificate details are available.
  • Basic reruns of the installer when a previous step was interrupted.

7.2 Not Supported Without Additional Approval

  • Installation on non-Ubuntu systems or unmanaged personal computers.
  • Use of unapproved servers, unapproved domains, or unapproved certificates.
  • Manual changes to database tables unless directed by an approved technical support process.
  • Sharing passwords, API keys, certificates, or patient data outside approved channels.
  • Custom clinical form changes that have not been approved by the clinical and Ministry stakeholders.
  • Changing the Data Pipeline schedule without agreement from the reporting and operations teams.
  • Using the cleanup script on a production server without written approval.

8. Troubleshooting Basics

8.1 General First Checks

  1. Check that the server is powered on and reachable.
  2. Check that the internet connection is working if the issue happened during installation.
  3. Check the latest deployment log for the affected service.
  4. Rerun the same deploy command if the installation stopped because of a temporary network issue.
  5. Record the time of the problem, the command that was running, and the message shown on screen.

8.2 Where to Find Logs

Service Log Location or Command
Node API deploy/node-api/logs/
WebEditor deploy/webeditor/logs/
Data Pipeline deploy/datapipeline/logs/
Metabase deploy/metabase/logs/ and sudo journalctl -u metabase -n 50

8.3 Common Installation Issues

Issue Likely Cause Basic Action
Installer says a required package is missing. The server does not yet have the required tool. Choose yes when asked to install the package, or ask the server administrator to install it.
Installer stops during download. The internet connection may be interrupted. Check connectivity and rerun the same command.
Metabase reports an invalid or corrupt jar file. The downloaded file may be incomplete or may be an error page. Rerun the Metabase deployer. The current deployer checks the file and downloads it again if invalid.
Metabase does not start on Ubuntu 24. Java may be older than required. Confirm that Java 21 or newer is installed, then rerun the Metabase deployer.
Data Pipeline does not run automatically. The scheduled task may not be installed or the virtual environment may be missing. Rerun the Data Pipeline deployer and confirm that the cron setup step completes.
Web page does not open using the domain. Domain records, nginx setup, or certificates may not be ready. Try the server IP address if approved, then rerun the relevant nginx setup phase after domain details are confirmed.

8.4 Safe Rerun Guidance

The installer records progress. If a step fails, rerun the same installation command after fixing the immediate issue. The installer should continue from the next unfinished step. If a full rerun is required, use FORCE_DEPLOY=1 only when approved by the responsible operator.

FORCE_DEPLOY=1 bash deploy/deploy.sh

8.5 When to Escalate

Escalate to the approved technical support contact if any of the following occur:

  • The server cannot be reached.
  • The database password is lost or exposed.
  • A production service is down and cannot be restarted.
  • Patient data may have been exposed or copied to an unapproved location.
  • The installer fails repeatedly after the same step.
  • The facility requires a change to clinical forms or reporting logic.

10. Final Operator Checklist

  1. The full installer completed or each required service installer completed.
  2. The WebEditor administrator details are recorded in the approved secure location.
  3. The Data Pipeline configuration files exist.
  4. The Data Pipeline scheduled task is installed.
  5. Metabase starts successfully.
  6. Any domain, IP address, and certificate choices are recorded.
  7. Installation logs are available for review.
  8. No passwords, API keys, or patient data have been copied into public documents.
